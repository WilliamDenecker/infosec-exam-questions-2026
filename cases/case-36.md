# Case 36

Deutsche Post has introduced a system of 'electronic stamp'. Instead of putting a regular stamp on an envelope, a software program allows you to generate electronic stamps (in PDF format) that you can print on your envelope. You do need Internet access for payment. An example of such an electronic stamp is given in Fig. 3.

**What security services are needed for proper security of this electronic stamp? What security mechanisms could have been used to achieve those? What threats are there to this security? What vulnerabilities might remain?**

*Some comments*:

- The program provides the following (mandatory) input fields:
  - The destination address (name – street and number – zip code – municipality)
  - The type of letter
  - The Date
- The question deals with the security of the stamp, not the security of the payment mechanism behind it to purchase the electronic stamps.
- In the example of Fig. 3 the real two-dimensional barcode on the right is replaced with a specimen (hence the German inscription "MUSTER", which of course does not appear on the real barcode)

## Answer

### Part 1 — Essential Security Services (ch1 p.10)

| Service | Required? | Slide | Why it is needed | What breaks without it |
|---|---|---|---|---|
| **Authentication / data-origin authentication** | Yes — critical | ch1 p.22 | A postal scanner must verify that the stamp was genuinely issued by Deutsche Post — not generated by anyone with a printer and some software. | Anyone prints a stamp without paying. Deutsche Post loses all revenue from electronic stamps. |
| **Data integrity** | Yes — critical | ch1 p.34 | The destination address, letter type, and date printed on the stamp must be bound to the stamp's authentication — changing any field after issuance must be detectable. | Attacker changes destination address on a purchased stamp (e.g., for domestic postage) to a different address or international destination. Or changes the letter type from "standard" to "express". |
| **Non-repudiation (of issuance)** | Yes | ch1 p.40 | Deutsche Post must not be able to deny having issued a valid stamp with specific parameters. | Deutsche Post denies a legitimately purchased stamp is valid; customer disputes cannot be resolved. |
| **Uniqueness / anti-replay** | Yes — critical | ch1 p.34 | Each stamp must be usable exactly once. A printed stamp (PDF) can be photocopied perfectly — without uniqueness control, one paid stamp yields unlimited free postage. | User prints stamp once, photographs it, prints 100 copies. Each letter carries the same stamp. All pass authentication. |
| **Confidentiality** | No | ch1 p.15 | The stamp data (address, letter type, date) is printed in human-readable form on the envelope. It is not sensitive. | Not applicable — the data is already visible. |

### Part 2 — What the Stamp Contains

The stamp is a printed 2D barcode (e.g., QR or DataMatrix) that encodes all necessary information plus a cryptographic proof of authenticity. The barcode is read by postal scanners at sorting facilities.

The stamp data:

```
stamp_data = {
    destination_address,    // name, street, postcode, municipality
    letter_type,            // standard / express / registered / etc.
    date,                   // date of intended posting
    serial_number,          // unique identifier for this stamp instance
    payment_reference       // links stamp to the paid transaction
}
```

Deutsche Post's cryptographic authenticator:

```
signature = ECDSA_sign(DP_private_key, SHA-256(stamp_data))
```

The 2D barcode encodes both `stamp_data` and `signature`. A postal scanner reads the barcode, recomputes `SHA-256(stamp_data)`, and verifies the ECDSA signature against Deutsche Post's public key.

### Part 3 — Signing Mechanism: Why ECDSA and Not HMAC

This is the most important design choice and requires careful justification.

**Option A — HMAC** (ch2.2.3 p.63–66): Deutsche Post computes `HMAC(K_DP, stamp_data)`. Every postal scanner needs K_DP to verify the HMAC.

**Why HMAC is rejected**: K_DP must be distributed to every postal scanner — potentially thousands, across Germany and internationally. Each scanner with K_DP can:
- Verify legitimate stamps (desired)
- **Also forge stamps** — compute valid HMAC for any stamp_data without paying

A single compromised scanner, or a single rogue postal employee with access to K_DP, can print unlimited valid stamps. The entire postage revenue model collapses. **HMAC cannot be used here because verification capability implies forgery capability with a symmetric key.**

**Option B — RSA-PSS** (ch2.2.3 p.88–93): Deutsche Post holds the RSA private key; scanners hold only the public key. Scanners can verify but not forge. Valid but:
- RSA-PSS signature at 2048-bit: **256 bytes = 512 hex characters**. A 2D barcode has finite data capacity. Encoding 256 bytes of signature plus all the stamp data fields requires a high-density barcode that may be difficult to reliably scan on a printed-and-photocopied page.

**Option C — ECDSA P-256 (chosen)** (ch2.2.3 p.85–87): Deutsche Post holds the ECDSA private key; scanners hold only the corresponding public key. Scanners can verify but not forge.

- ECDSA P-256 signature: **64 bytes** — 4× smaller than RSA-PSS at equivalent security
- Deutsche Post's public key is freely published — any scanner, anywhere in the world, can be given the public key without risk. A public key cannot forge signatures.
- Only Deutsche Post's private key (held offline and highly secured) can produce valid signatures.

**Why 64 bytes matters**: the barcode must also encode the stamp_data (address, type, date, serial) — already a significant payload. Reducing the signature from 256 bytes (RSA) to 64 bytes (ECDSA) makes the barcode substantially smaller, more reliable to print and scan, and more tolerant of print quality variations.

### Part 4 — Preventing Reuse: Serial Numbers and Central Database

A stamp is a PDF — it can be photocopied indefinitely. Every copy carries exactly the same barcode, the same stamp_data, and the same valid ECDSA signature. Cryptographic signature verification alone **cannot prevent reuse** because the signature on each copy is identical and equally valid.

**Solution — Unique serial number + central used-stamp database**:

Each stamp receives a **unique serial_number** at purchase time (included in stamp_data and covered by the ECDSA signature). Deutsche Post maintains a database of used serial numbers:

```
At each postal processing point:
  1. Scanner reads barcode → extracts { stamp_data, signature }
  2. Verify ECDSA signature → confirms Deutsche Post issued it
  3. Check serial_number against central database:
     If serial_number already marked as used → reject (copy detected)
     If serial_number not seen before → mark as used → accept
```

**Why the serial_number must be in the signed stamp_data**: without it in the signed data, an attacker could take a valid stamp, modify only the serial_number field (not covered by the signature), and present it as unused. The signature must cover serial_number to bind it cryptographically.

**Why this works against photocopying**: the first envelope to arrive at a sorting facility gets the serial_number marked as used. Every subsequent copy of the same stamp presents the same serial_number — already marked used → rejected.

**Offline scanner limitation**: a scanner without network access cannot check the used-stamp database. A copied stamp would pass cryptographic verification (signature valid) and succeed at an offline scanner. This is a residual vulnerability inherent to offline operation — mitigated by online database checks at central sorting facilities (where high-volume scanning occurs) and accepting offline risk at peripheral points.

### Part 5 — Date Binding

The stamp includes a specific `date` field (covered by the signature). Postal rules define a validity window around this date (e.g., ±3 days). A stamp for 2026-05-23 is not valid on 2026-06-01.

**Why date binding matters**: without it, a user could buy a stamp in bulk during a promotional period and use them months later (potentially after postage price increases). Date binding ties each stamp to its purchase context. An attacker cannot purchase one stamp and use it indefinitely.

### Part 6 — Security of Deutsche Post's Private Key

The ECDSA private key is the single most valuable secret in the system. If it is compromised:
- The attacker can sign any stamp_data → unlimited free postage for any destination, any letter type
- All existing deployed scanners continue to accept forgeries (they trust the key)
- Recovery requires a full key rotation: new key pair, update all scanners with new public key

**Key protection measures** (outside scope of stamp protocol, but necessary):
- Private key stored offline in air-gapped hardware
- Key ceremony with multiple authorised personnel required to use the key for stamp signing batch operations
- New stamps are signed in batches; the private key is not exposed to internet-connected systems

**Why key rotation is the contingency**: if the private key is compromised, Deutsche Post generates a new ECDSA P-256 keypair, distributes the new public key to all scanners (via authenticated software update), and accepts a period of dual-key operation for in-flight stamps signed under the old key.

### Part 7 — Stamp Verification at Scanner (Full Protocol)

```
Scanner reads 2D barcode → decodes { stamp_data, signature }

Step 1 — Data extraction:
         Parse { destination_address, letter_type, date, serial_number, payment_reference }

Step 2 — Cryptographic verification:
         Recompute hash: h = SHA-256(stamp_data)
         Verify: ECDSA_verify(DP_public_key, h, signature)
         If FAIL → reject (forgery or corrupted barcode)

Step 3 — Date check:
         Is current date within validity window of stamp date?
         If NO → reject (expired or future-dated stamp)

Step 4 — Serial number check (if online):
         Query central DB: is serial_number already marked used?
         If YES → reject (copy/reuse attempt)
         If NO  → mark as used; accept

Step 5 — Accept letter for processing
```

### Part 8 — Threats and Vulnerabilities

| Threat | Attack | Why it fails (or doesn't) |
|---|---|---|
| **Stamp forgery** | Attacker generates stamp without paying | Requires DP private key; ECDSA forgery infeasible without it (ch2.2.3 p.85–87) |
| **Stamp copying / reuse** | Prints multiple copies of same stamp | Serial number database: first use marks it spent; copies rejected |
| **Field modification** | Changes address or letter type after printing | Signature covers all stamp_data; any change invalidates signature |
| **Old key forgery** | Compromise of old private key after rotation | Validity window + date binding limits usefulness; scanner updates reject old key |
| **Offline scanner bypass** | Uses copy at offline scanner | Serial number check cannot occur; copy accepted once at offline scanner. Residual risk. |
| **Database unavailability** | DB down → all scanners go offline | Serial number check skipped at offline scanners; copies may pass. High-availability DB mitigates. |

### Part 9 — Why the Hash (SHA-256) Before ECDSA

ECDSA signs a **hash** of the stamp_data, not the raw data:

```
signature = ECDSA_sign(DP_private_key, SHA-256(stamp_data))
```

**Why hash first?** ECDSA operates on integers in a fixed range (the curve order). Direct signing of arbitrary-length data is not defined. SHA-256 maps any-length input to a fixed 256-bit output that fits the curve's scalar field. Additionally, hashing before signing prevents certain algebraic attacks on the signature scheme.

**Why SHA-256 and not SHA-512?** ECDSA P-256 uses a 256-bit curve order; the hash output should match this size. SHA-256 produces 256 bits — a natural match. SHA-512 produces 512 bits (truncated to 256 for P-256); no security benefit, slightly larger computation.

### Part 10 — Summary of Design Choices

| Component | Chosen Solution | Slide reference | Why better than alternatives |
|---|---|---|---|
| Stamp authentication | ECDSA P-256 signature by Deutsche Post | ch2.2.3 p.85–87 | Public key freely distributable without forgery risk; HMAC gives scanners forgery capability; RSA-PSS produces 256-byte signature vs 64-byte ECDSA (4× larger barcode) |
| Hash before signing | SHA-256(stamp_data) | ch2.2.3 p.24–32 | Maps variable-length stamp data to fixed 256-bit value matching P-256 curve; prevents algebraic attacks |
| Anti-copy / uniqueness | Unique serial_number in signed data + central used DB | ch1 p.34 | PDF can be photocopied; signature cannot detect copies; serial uniqueness is the only copy-resistance mechanism |
| Date binding | Date field in signed stamp_data, validity window | ch1 p.34 | Prevents indefinite stockpiling; timestamps for freshness (ch3.1 p.3) |
| Key protection | DP private key offline; air-gapped signing | ch3.7 p.46 | Only protection if private key is compromised; internet-connected key is maximum risk |
| Why not HMAC | Verification capability implies forgery capability | ch2.2.3 p.63–66 | Symmetric key distributed to thousands of scanners; one compromised scanner forges unlimited stamps |
